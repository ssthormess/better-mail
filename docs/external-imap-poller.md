# External IMAP polling (F37)

The first poll starts at UID 1 and imports existing mail oldest-first. `UIDVALIDITY` must be a canonical positive uint32 and `UIDNEXT` must be a positive uint32; a missing/invalid value fails without advancing state. Search is bounded to `[startUid, min(startUid + 999, UIDNEXT - 1)]`, so even a 4,000-message inbox cannot exceed the IMAP response-line bound. At most 50 candidate UIDs are fetched per poll; if a window is fully scanned, the cursor advances through its empty UID gaps. Repeated polls continue with the next bounded window. The uint32 ceiling completes without issuing an invalid N+1 query.

Each candidate gets a `UID FETCH (UID RFC822.SIZE)` first. Only a closed, tokenized FETCH record whose UID and RFC822.SIZE match the request can authorize an oversized skip. A size above 5 MiB is recorded and advanced without fetching the body. The full body FETCH is then checked against the size result and exact UID/attribute; mismatches fail without advancing. Additional flags-only FETCH records are ignored. A tagged OK without the requested record triggers a targeted `UID SEARCH UID N:N`: confirmed absence is treated as an expunge, while a still-present UID is an unexpected response and fails the poll. Completed messages are stored and checkpointed one at a time, so a later failure does not discard earlier progress.

`sync_cursor.skippedUids` keeps the most recent 128 permanently oversized UIDs. The account API exposes that bounded list as `skippedUids`, never the raw cursor. `last_error` remains a warning while the list is non-empty; later successful polls do not clear it. The warning/diagnostics reset only when the upstream source is changed (which resets the cursor) or the remote UIDVALIDITY epoch changes. The cursor codec rejects incomplete IMAP objects, except the empty object retained as a legacy no-state value.

## Scheduling and claims

Polling runs every minute in the self-hosted Node scheduler. A local in-flight guard avoids overlapping ticks in one process. Candidate SQL filters active cross-process claims and the current process's retry-backoff IDs before applying the ten-account limit; NULL last-sync values sort first. The process-local failure map is pruned for removed/disabled accounts and resets on restart. Failed polls persist only fixed, sanitized errors and back off from two minutes up to 30 minutes.

Before any network or intake work, the poller atomically acquires a database lease on the account. The unique random claim token and expiry are stored in `poll_claim_token`/`poll_claim_until`; heartbeats stop at the account deadline, and the lease expiry is capped at that deadline plus a short release grace. The token, source identity, cursor snapshot and unexpired lease are checked on every cursor write. PATCH/DELETE are refused while a live claim is held, and source-changing PATCH uses compare-and-update against the settings it read before resetting the cursor. Claim fields are transient and omitted from backups. A crash releases the lease by expiry. Per-tick/account absolute deadlines pass through the socket client and intake; database and storage awaits also have short operation deadlines. A timed-out operation is observed without holding the tick open, and pending work cannot renew the lease. Timed-out content-addressed raw PUTs are never deleted: they may already be referenced by an older message, so an unreferenced late object is preferable to breaking stored mail. If intake finishes after its deadline, the cursor is not advanced and an idempotent retry can complete it.

The tick budget is 50 seconds; each account's IMAP session is capped at the earlier of the tick deadline and 45 seconds. Commands, DNS, and TLS handshakes are capped at 12 seconds; individual database and storage operations are capped at five seconds (cleanup/release gets at most one second). Socket reads are bounded to 32 MiB, metadata to 512 KiB, a search window to 1,000 UIDs (under the 16 KiB line cap), and each batch to 50 messages/20 MiB with each message capped at 5 MiB. Permitted DNS addresses are tried in resolver order under the same session deadline, dialing only their checked numeric addresses; STARTTLS setup failure tries the next checked address without falling back to plaintext.

## Runtime, TLS, and egress

This poller supports self-hosted Node only. The Worker scheduled handler does not invoke it because workerd sockets use a different API. A minimal RFC 3501 client uses Node `net`/`tls`; implicit TLS and STARTTLS verify certificates and the original hostname. `tls_mode=none` sends LOGIN and mail in plaintext and is intended only for trusted local networks. Credentials with unsupported IMAP string characters are refused rather than serialized unsafely.

By default every resolved A/AAAA answer must be public/routable. Resolution is repeated before dialing, and the checked numeric IP is used for the connection, preventing DNS rebinding to a private address. Operators who intentionally fetch from LAN IMAP may set `EXTERNAL_FETCH_ALLOW_PRIVATE=1`; this host-wide trust decision permits full-access mailbox delegates to configure private destinations. Do not set it where mailbox managers are untrusted.

## Historical-import policy

All IMAP mail uses `intakeMode: "historical_import"`, including newly arriving messages. It still runs MIME parsing, routing/folder rules, spam classification, message storage, FTS indexing, and threading. It does **not** ingest DMARC aggregate reports, train/update spam reputation, register calendar invitations (and therefore creates no reminder), send auto-replies, notifications or webhooks, create auto-drafts, process DSN bounces, or look up avatars. DMARC-report mail addressed to the report endpoint is discarded; its unreferenced raw object is left for the orphan sweeper. Normal SMTP/Worker queue intake keeps real-time behavior by omitting this mode.

Raw mail is passed through `processInboundMessage`. Its deterministic raw key hashes mailbox ID plus exact RFC822 bytes. Historical intake verifies the object exists before processing; a missing object fails the poll so the UID is retried. Rejection, routing-drop, parse-drop and historical-report paths do not eagerly delete raw keys, since replay keys may already be referenced; the age- and reference-aware sweeper is their only cleanup path. Objects become eligible after 24 hours, but actual reclamation may take later daily passes as a persisted, bounded key-ordered scan advances through the bucket. The message-reference write and object deletion share a database fence: transactional drivers hold the fence across the final object check/write and row insert, while D1 uses pending-delete rows plus insert triggers. A D1 claim is released only after R2 confirms deletion and that completion is recorded; uncertain claims remain fail-closed instead of risking a late delete against a replay. Drivers without interactive transactions fail closed and do not sweep raw mail. The bucket-local scan cursor is deliberately omitted from backups and starts over after restore. New message rows start with `intake_complete=false`; intake marks them complete only after attachment rows and objects are persisted. A replay skips only a completed row. If an insert or attachment write outlives its deadline, the incomplete row is repaired from raw MIME on retry, using deterministic per-message attachment IDs/keys so overlapping attempts converge rather than duplicate or delete each other's objects. The false-to-true completion transition is also the durable winner claim for normal post-intake effects; only its winner sends notifications, replies, DSNs or webhooks. It is not an outbox: a crash after this transition but before those effects can lose them, while replay will see the completed row and not re-emit them. Existing message rows default to complete.
