# External IMAP polling (F37)

The first poll of an account starts at UID 1 and fetches the first 50 messages, then continues from its durable cursor on later ticks. This intentionally imports old mail oldest-first; it does not silently treat an account's existing mail as already imported. A UIDVALIDITY change resets the effective UID to 1 and replays the mailbox in bounded batches. The raw-message content key is scoped to the destination mailbox, so a replay is idempotent in `processInboundMessage` even if storage succeeded before a crash prevented the cursor update.

Polling runs every minute in the self-hosted Node scheduler. It considers the ten oldest enabled IMAP rows due by the indexed `(enabled,last_synced_at)` scan, processes accounts serially, batches at most 50 messages, caps a fetched message at 5 MiB, and stops starting accounts after a 25-second tick budget. An in-process account set prevents overlapping polls in one Node process. Failed polls persist only fixed, sanitized messages and progressively back off from two minutes up to 32 minutes in process; after restart the counter resets, so failure backoff starts at one minute. Credentials are decrypted only for the active connection and are never logged or returned in persisted errors.

No IMAP dependency existed. `imapflow` was not added: a Node stream/socket client is not usable in workerd, while the required client must run with Node TLS semantics and certificate verification. This implementation uses a minimal RFC 3501 client over Node `net`/`tls`, with implicit TLS, STARTTLS, or plaintext as configured. TLS verification is always enabled; there is no skip-verify option. `tls_mode=none` sends the IMAP `LOGIN` command (username and password) and fetched mail in plaintext; it is intended only for trusted local networks. The client accepts `BODY[]` and `RFC822` literal response attributes and does not assume the UID precedes the literal; untagged responses such as `EXPUNGE` are skipped while waiting for the matching tagged completion.

This release deliberately supports self-hosted Node only. The poller imports Node sockets and Cloudflare workerd's `cloudflare:sockets` transport is a separate API, so the Worker scheduled handler does not invoke it; the code comments make this limitation explicit rather than silently claiming D1 support. Messages go through the existing `processInboundMessage` consumer after raw bytes are stored, preserving parsing, spam, rules, indexing, threading and its `(mailboxId, rawR2Key)` deduplication.
